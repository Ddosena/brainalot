# Разговорная нарезка кубиков

Статус: предложение режима, не готовая функция. Основание — запрос владельца
24октября2026: вместе с агентом во время разговора менять кубики, добавлять
новые и сразу видеть изменения. Удаление кубика реализуется отдельным этапом;
этот документ не означает готовность всего режима нарезки.

## Выбранный подход

Нарезка работает с общим пулом этапов одной выбранной задачи. Пользователь
разговаривает с агентом в Codex, Work остаётся открытым рядом. После законченной
фразы агент выполняет одну небольшую типизированную операцию. Цепочка на экране
меняется сразу; агент коротко сообщает результат и новую сумму минут.

Не нужен ещё один чат внутри Brainalot, отдельный платный вызов модели или
постоянно слушающий микрофон. Ввод — текущий разговор с агентом, запись — общий
CLI/API Work. Агент не управляет мышью и не угадывает интерфейс по скриншоту.

Пул — сохранённый черновик состава работы. Его редактирование не запускает
таймер и не набирает день автоматически. Отбор в день и «Закрепить пул» остаются
существующими действиями. Не вводить вторую обязательную кнопку подтверждения
каждого безопасного переименования. Изменения в пуле видны и сохраняются сразу;
для последней операции нужна адресная отмена.

## Как проходит разговор

1. В Work пользователь открывает «Нарезку» и выбирает задачу. Название родителя
   и цепочка его этапов остаются перед глазами; сохраняются компактные блоки.
2. Пользователь: «Раздели подготовку примеров на поиск и проверку — по20минут».
   Агент читает выбранную задачу, кубик и текущую ревизию, затем одним действием
   заменяет неначатый40-минутный кусок двумя20-минутными.
3. Пользователь: «Проверку поставь после сборки сцены, а поиск назови короче».
   Меняются порядок и название; сумма времени и факты не затрагиваются.
4. «Добавь проверку толщины на15минут» создаёт новый этап с результатом.
   Если это увеличивает оценку задачи, Work явно показывает новую сумму;
   дневной лимит энергии сам не увеличивается.
5. «Верни последнее» отменяет только последнюю правку нарезки. Завершение режима
   оставляет согласованный пул, из которого пользователь дальше набирает день.

Если время не названо, новый этап может появиться как «Оценить время»;
такой черновик нельзя брать в день. Не выдавать выдуманную длительность за
согласованную оценку. Готовность и фактическое время остаются отдельными полями.

## Операции первой версии

| Действие | Результат | Ограничение |
|---|---|---|
| Добавить этап | Название, минуты, ожидаемый результат и шаги | Известный родитель и явная оценка перед набором в день |
| Изменить | Название, длительность, результат, шаги | Не менять идентичность источника |
| Разделить | Несколько новых кубиков вместо одного | Только неначатая часть; одна атомарная замена |
| Объединить | Один кубик вместо нескольких | Один родитель/этап, без начатой работы |
| Переставить | Новый логический порядок этапов | Сохраняются ID и связи |
| Удалить | Убирается конкретный этап | Родитель не удаляется неявно |
| Отменить правку | Адресное восстановление предыдущих полей | Не откатывать весь Work и чужие изменения |

У новой операции должно быть понятное резюме: «40→20+20мин», «добавлено15мин»,
«порядок изменён». Постоянные технические ID в интерфейсе не нужны. При фразе
«этот кубик» агент получает реальное выделение через API. Если выделения нет
или название неоднозначно, он уточняет конкретный этап.

## Границы родителя и источника

Уже принятое правило владельца: удалить этап можно отдельно; целую задачу —
только отдельным действием. Текущий самостоятельный Brainalot-кубик связан
с одной заметкой через проверяемыйsource_ref. Его удаление удаляет эту запись.
Work-кубик большой задачи удаляет только выбранную часть, сохраняя родителя.

Для нарезки одной Brainalot-задачи на несколько кубиков нужна явная модель
дочерних этапов: parent noteID + отдельный stageID. Сейчас source_ref уникален
для Brainalot-кубика, поэтому просто размножить его нельзя. Все дети могут
наследовать важность родителя, но удаление ребёнка не должно удалять общую
заметку. Последний удалённый ребёнок также не означает удаления родителя.

Не создавать отдельную библиотечную заметку на каждый служебный15-минутный
кубик. Этапы хранятся в Work и могут показываться в раскрытии исходной задачи.
Нельзя связывать записи по совпадению названия, проекту или source_capture_id.

## Что уже есть и чего пока нет

Есть общий CAS/receipts Work, сохранение через
`mmm work plan command --file`, создание/правка constructor_cube, segment_create,
describe_cubes, выбор/возврат/перемещение, бюджет и независимые факты.
Открытый Work принимает внешние ревизии; текущий poll вwork-store.js —5секунд.
Начальная правка метаданных агентом возможна через существующие команды.

Ещё нет пользовательского режима нарезки, атомарной split/merge, общих
идентификаторов дочерних этапов Brainalot, адресной отмены операции нарезки
и передачи выделения агенту. Нельзя объявлять их реализованными на основании
того, что одиночный constructor_cube уже работает.

## Минимальная техническая реализация

- Контекст выделения хранится отдельно от фактов плана. Клик по кубику не должен
  менять Workrevision и конфликтовать с записью готовности.
- В активном режиме проверять внешние изменения примерно раз в секунду;
  вне режима оставить обычную синхронизацию. Новый WebSocket-сервер не нужен.
- Агент использует короткие типизированные операции с request_id, ревизией
  и проверкой исходных полей. Повтор одного запроса не создаёт второй кубик.
- Разделение/объединение — одна серверная операция с lineage старых и новых ID.
  Это **замена**, а не последовательность delete+create: настоящее удаление
  отменяет оставшийся объём, тогда как нарезка обязана его сохранить.
- При конфликте чужая правка не перезаписывается. Work показывает сохранённую
  версию и несохранённый ввод раздельно. Удалённый кубик не пересоздаётся из
  старого popupчерновика.
- Изменения названий допустимы без сброса фактов. Начатые/завершённые кубики
  не дробятся и не объединяются задним числом. Таймер не переносится молча
  на новый ID; нарезается только свободный неначатый остаток.
- Действие явно различает отменённую работу, заменённые кубики и выполненную
  работу. Удаление не становится готовностью и не выдаёт награды.

Названия новых API действий следует зафиксировать при реализации; перечисление
выше не является списком уже доступных команд. Предпочтителен один backendbatch
на одну смысловую фразу, с итогом и адресной отменой.

## Проверка перед показом владельцу

Открытый Work + команды из второго процесса: изменения видны, не нужен reload.
Повтор команды, две конкурирующие правки, потеря ответа, отмена, закрытие и
возобновление разговора не дублируют кубики. Split/merge сохраняют сумму минут,
родителя и прогресс; удаление одного ребёнка не удаляет остальных и исходную
задачу. Повторный импорт/пересчёт не возвращает отменённые или заменённые куски.

После контракта нужен небольшой интерактивный прототип на той же цепочке
компактных кубиков; перенос нового режима в приложение — после просмотра
владельцем. Текущая реализация удаления не подменяет эту следующую приёмку.
