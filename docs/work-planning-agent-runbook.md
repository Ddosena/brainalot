# Агент: короткий цикл планирования Work

Этот цикл применяется к просьбам о прогрессе, переносе остатка и разборе следующей недели в существующем Work. Источник состояния — WorkStore через общий CLI, а не история разговора, Google-таблица или весь учебный корпус. Не перечитывайте материалы курсов без конкретной необходимости.

## Конструктор дня, начиная с Work 0.2.12

Главный экран — ручной набор компактных кубиков. Календарная шкала содержит только события; кубикам не назначаются обязательные часы начала. AUTO-кубики двухмесячного расчёта — прогноз, а не выбранный пользователем набор. Ручной набор, порядок, готовность и фактическое время сохраняются при пересчёте.

Одна энергия = 60 минут общей нагрузки. `day_budget {date,minutes}` меняет бюджет отдельного дня (0–480 минут, шаг 15). По умолчанию 300 минут; увеличивать его автоматически запрещено. Явное пользовательское изменение ползунка — решение для конкретного дня. Уроки учитываются всегда; `prep_set {prep_id,minutes}` меняет отдельную подготовку от 0 до 120 минут с шагом 5.

Для сборки использовать `day_cube_add {date,task_id,minutes,segment_id?}` (15/30/45/60/90 минут), `day_cube_remove {cube_id}`, `day_cube_move {cube_id,date,index?}` и `day_cube_resize {cube_id,minutes}`. Новый свободный бюджет не заполняется автоматически. Начатая работа не удаляется ради красивой сетки.

Иерархия: курс → материал/большая задача → этап → кубики. `segment_create {task_id,title,minutes,output?,steps?}` выделяет этап из существующего объёма задачи, не добавляя часы к оценке. `day_segment_add {date,segment_id,minutes?}` атомарно набирает последовательность кубиков этапа в день. `segment_progress {segment_id,percent}` — явная оценка готовности этапа; её нельзя складывать повторно с готовностью его кубиков. При снятии лишних неначатых резервов сообщить пользователю результат операции.

«Приступить» использует общий TimeStore: `source=work`, `id=work-cube:<cube_id>`, режим pomodoro, длительность кубика. Отдых и следующий запуск выбирает пользователь. Истечение таймера не означает готовность. `cube_progress`/`prep_progress` сохраняют процент и фактические минуты отдельно. Не запускать другой таймер и не создавать библиотечные заметки для служебных кубиков.

## Начало любого обращения

```powershell
.venv\Scripts\python.exe -m megamozg work plan status
```

В установленном пакете можно использовать `mmm work plan status`. Для другого корня данных явно передайте `--root` перед `work`. Сводка содержит ревизию, актуальность календаря, фактический прогресс, оставшиеся минуты, ближайшие дни/кубики и риски. Достаточно её и нового сообщения пользователя. Если требуется точный состав отдельной задачи, читайте только её ресурс или связанное Work-описание.

Потраченное время и готовность независимы. Не отмечайте материал выполненным только потому, что таймер прошёл плановое время. Сохранённые проценты и явно заданный остаток важнее старой полной оценки. Не превращайте неизвестную оценку или неназначенный эфир в ноль.

## Обычный перенос остатка

1. Прочитать сводку. Сопоставить новые сведения с сохранёнными процентами и итогом дня; не записывать их повторно как дополнительный прогресс.
2. Если пользователь сообщил результат только в чате, записать `cube_progress` или `day_outcome` через типизированную команду ниже. Для результата дня достаточно фактического остатка и короткого комментария.
3. Пересчитать только будущую часть. Дату выбирать в часовой зоне плана: обычно завтра, а при явной просьбе перестроить ещё не начатый сегодняшний день — сегодня.

```powershell
.venv\Scripts\python.exe -m megamozg work plan replan --from YYYY-MM-DD --reason "Перенос фактического остатка после итога дня" --refresh-calendar
```

4. Проверить результат: сумма нагрузки, сохранённые закрепления, просрочки, нераспределённые эфиры и свежесть календаря. Если календарь не подтверждён или времени не хватает, сказать это конкретно, не объявлять сетку выполнимой.
5. Ответить коротко: что сделано; что осталось; какие 2–3 даты изменились; где нужен вынужденный дополнительный час или уточнение.

Обычный лимит — 5 часов всей работы. В него входят уроки, подготовка, эфиры, курсы и недельный разбор. Дополнительные часы допускаются только как объяснённое вынужденное исключение в свободный от уроков день, с явной причиной и установленным пределом. Не повышать лимит из-за одной только грубой начальной оценки. Учитывать уже данное в беседе разрешение пользователя; не запрашивать его повторно для того же согласованного исключения. Фактические дедлайны не сдвигать, чтобы скрыть дефицит.

## Задача конца недели

В Work есть отдельная задача «Спланировать следующую неделю с агентом». Её время включено в нагрузку. Во время разбора:

1. Сверить факты прошлой недели и незакрытый остаток.
2. Обновить календарь и проверить дедлайны/даты эфиров.
3. Уточнить только неизвестные остатки, влияющие на следующую неделю.
4. Сначала пересчитать часы и размещение, затем детализировать кубики ближайших 7 дней: конкретное действие, 2–5 шагов и проверяемый результат.
5. Сохранить детализацию и отметить проведённый разбор. Непроведённый разговор нельзя автоматически считать выполненным.

Горизонт на два месяца остаётся общим ориентиром. Не переписывайте все будущие кубики ради недельного разбора. Конкретные шаги сохраняются в Work, чтобы их видел пользователь и следующий агент. При перестановке подробно описанных кубиков проверить предупреждение о несовпавших деталях, затем привязать их к новой сетке.

## Запись прогресса и конкретных шагов

Подготовить небольшой UTF-8 JSON-файл в приватном каталоге данных. Команда содержит ровно `request_id`, `expected_revision`, `action`, `data`. Свежую ревизию брать из status, `request_id` создавать один раз на действие; при неопределённом ответе повторить тот же файл, а не новое действие.

```powershell
.venv\Scripts\python.exe -m megamozg work plan command --file data/work-command.json
```

Действия: `cube_progress` (cube_id, percent, actual_minutes), `day_outcome` (task_id, date, remaining_minutes или done, note), `describe_cubes` (entries с cube_id, title, output, steps), `weekly_review_done` (id, done), `place_cube` (cube_id, date, start, locked), `resource` и `capacity_override`. Используйте реальные ID из сводки и точную схему установленной версии. Не редактируйте SQLite, JSON blob или план через обычный Work commit в обход проверок. Конфликт версии требует нового чтения и осмысленного повторного применения; один request_id нельзя использовать с другим содержимым.

Разбор или пересчёт не отправляет сообщений другим людям, не меняет Google Calendar и не вызывает платную модель. Агент работает при обращении пользователя; фоновая генерация не обещается.
