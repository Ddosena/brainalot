# Work: контракт конструктора дня, 23.10.2026

Статус: согласованный контракт реализации A/backend — Б/UI — root. Работа идёт через существующий POST /api/work/planning с request_id, expected_revision, CAS и общими ревизиями Work. Calendar только читается; lesson events не изменяются. Обычный бюджет 300 минут, 1 единица энергии = 60 минут всей работы.

## Actions

| action | data | эффект |
|---|---|---|
| day_budget | {date,minutes}; дата YYYY-MM-DD, 0…480, шаг 15 | Установить бюджет только этого дня. Больше 300 — явное решение пользователя, raised_load=true даже при уроках. |
| prep_set | {prep_id,minutes}; 0…120, шаг 5 | Изменить отдельную подготовку к уроку; 0 скрывает её занятость, исходные 25 восстанавливаются. Урок остаётся неизменным. |
| prep_progress | {prep_id,percent,actual_minutes?} | Отдельно сохранить процент и фактические минуты подготовки; остаток большого материала не меняется, таймер не завершает кубик сам. |
| day_cube_add | {date,task_id,minutes,segment_id?,index?}; размер 15/30/45/60/90 | Сервер создаёт устойчивый cube_id и резервирует плавающий ручной кубик в последовательности дня; start не нужен. |
| day_cube_remove | {cube_id} | Вернуть не начатый кубик в пул; факт и начатый кубик не удаляются. |
| day_cube_move | {cube_id,date,index?} | Переставить не начатый кубик по дню/порядку, сохранив ID и детали. Начатый не перемещается. |
| day_cube_resize | {cube_id,minutes}; 15/30/45/60/90 | Изменить длительность не начатого ручного кубика без смены ID, деталей и порядка; проверить бюджет и остаток. |

Первое typed редактирование переводит день в ручной режим: сохраняются начатые/отчитанные и явно закреплённые кубики с прежними ID, а неначатый AUTO-прогноз не переносится в выбранный набор. Свободное место **не заполняется автоматически**. Остальные AUTO-дни могут перестроиться с учётом ручных резервов. Ручной день допускает несколько выбранных задач; AUTO-день сохраняет одну фокусную задачу. Typed действия cube_progress, day_outcome, describe_cubes и недельного разбора остаются прежними.

## Хранилище и read model

- planning.manual_days: map date -> {budget_minutes}. Наличие даты означает manual; без записи используется settings.day_limit_minutes. planning.prep_overrides: map prep_id -> minutes. Ручные кубики живут в planning.locks с manual:true и locked:true, сохраняются при replan и seed import.
- result.days[] получает budget_minutes/day_limit_minutes, energy_units=budget_minutes/60, manual, raised_load, over_cap_minutes, prep_cubes[], builder_selected_minutes, builder_total_work_minutes, builder_available_minutes, builder_over_cap_minutes. Builder-поля игнорируют неначатый AUTO-прогноз. fixed_minutes включает уроки, выбранные подготовки и календарный резерв; total_work_minutes добавляет выбранные рабочие кубики и недельный разбор. prep_actual_excess_minutes объясняет подтверждённое превышение выбранной длительности подготовки.
- result.days[].prep_cubes[]: {id,calendar_event_id,date,lesson_start,minutes,default_minutes:25,floating:true}; ID устойчив по occurrence урока. При 0 запись остаётся в read model для действия «Вернуть».
- result.cubes[] ручной кубик: {id,task_id,date,minutes,manual:true,locked:true,floating:true,start:null,end:null,order:int,is_remainder:false,...}. Короткий ручной размер не выдаётся за автоматический хвост задачи. Старые AUTO-кубики со временем начала и конца сохраняются для совместимости.
- result.task_pool[]: ближайшие активные задачи с task_id,course,title,due,due_status,remaining_minutes,manual_reserved_minutes,auto_future_minutes,available_for_manual_minutes. Факт и ручные резервы вычитаются. AUTO-план показан отдельно и может уступить место ручному выбору без двойного счёта.
- result.tasks[].remaining_minutes — текущий подтверждённый остаток, включая ноль у завершённой задачи; remaining_at_horizon_minutes — отдельный прогноз.

## Этапы внутри большой задачи

planning.task_segments[] хранит локальные этапы {id,task_id,parent_id:null,title,minutes,steps?,output?,origin:auto|manual}; начальные auto-этапы строятся из существующих STEPS, каждый не длиннее 300 минут, сумма равна базовому остатку родительской задачи. Этапы **разделяют**, но не увеличивают её объём. planning.segment_progress[id]={percent,date,cube_credit_at_report}; result.task_pool[].segments показывает оставшийся объём, процент и шаги. Кубик может иметь segment_id. После явного процента effective credit этапа равен explicit credit + прирост cube credit после сохранённого якоря, с ограничением размером этапа; до явного процента учитываются только кубики. Это исключает двойной счёт и позволяет завершить остаток кубиками после 50%.

Граница совместимости: старые и вспомогательные AUTO-кубики без segment_id остаются связанными только с большой задачей. Их процент уменьшает parent remaining, но не приписывается произвольно конкретному этапу. Новый ручной кубик, выбранный внутри этапа, передаёт segment_id и учитывается в нём.

Новые typed actions: segment_create {task_id,parent_id?:null,title,minutes,output?,steps?} принимает 15…300 минут с шагом 15 и вырезает минуты из ещё не начатых auto-этапов этой задачи; segment_progress {segment_id,percent} задаёт абсолютную готовность этапа; day_cube_add принимает optional segment_id. day_segment_add {date,segment_id,minutes?} атомарно добавляет плавающую последовательность кубиков из 90/60/45/30/15 минут; удобно выбрать 120/180/240/300, а по умолчанию берётся доступный остаток до 300. Если всё не помещается в энергетический бюджет или остаток этапа, не записывается ни один кубик. Когда процент этапа сокращает остаток ниже выбранных ещё не начатых кубиков, сервер явно возвращает лишние резервы в пул и сообщает их ID в result.released_reservations; факт и начатые кубики сохраняются. plan_version включает все ручные бюджеты, подготовки, этапы и проценты; Work revision остаётся CAS-источником истины.

Общий timeline показывает только Calendar. Подготовка привязана к конкретному уроку и расходует энергию, но не занимает фиксированный часовой слот в конструкторе. Ручные кубики идут в порядке order; пользователь запускает Pomodoro для выбранного кубика и сам выбирает момент следующего. Таймер не закрывает кубик автоматически: готовность/факт меняют только явные typed actions. Прежние часы AUTO-кубиков сохраняются в данных для совместимости, но UI может скрывать их. CAS, request_id и типизированная валидация применяются до записи.

Если новый бюджет не вмещает **не начатые** выбранные кубики, action возвращает 422 с требованием сначала вернуть или переставить кубик. Уроки и подтверждённые фактические минуты при снижении бюджета сохраняются; перегрузка показывается, не скрывается и не вызывает автоматического увеличения энергии. 0 энергии допускается как явный выбор. Прогресс и day_outcome относятся к отдельному кубику/задаче и **не закрывают весь день**: сегодня можно добавить другую задачу в свободный остаток. Отчётный факт не пересчитывается. Прошедшие даты остаются read-only, без переноса начатых кубиков.

Для старого planning.result без новых полей root после backup выполняет ровно один typed recalculate с актуальной revision без обновления Calendar, до открытия нового UI. Схема старого state.planning принимается; после пересчёта новый read model сохраняется в очередной ревизии. Это не меняет статусы и не подменяет выполненную работу.

Приёмка: день 255 минут уроков и подготовок при бюджете 300→360; prep25→0→25 без автозаполнения; ручные размеры 15/30/45/60/90; снижение ниже fixed+actual разрешено с видимой перегрузкой, ниже fixed+actual+unstarted отклонено; добавление другой задачи сегодня после 50% первого кубика или day_outcome по первой задаче; ручной день переживает replan/import; удалить/двигать начатый нельзя; разные задачи не дублируют future AUTO; CAS и повтор request_id.
